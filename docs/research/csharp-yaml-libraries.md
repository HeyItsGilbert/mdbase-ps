# C# YAML libraries for Mdbase.Core

Research for [Decide C# YAML library for the Core Engine](https://github.com/HeyItsGilbert/mdbase-ps/issues/28), part of the [mdbase-ps implementation plan](https://github.com/HeyItsGilbert/mdbase-ps/issues/1). Supersedes [Survey PowerShell YAML frontmatter parsing options and dependency policy](https://github.com/HeyItsGilbert/mdbase-ps/issues/5) (full survey: [yaml-frontmatter-parsing.md](yaml-frontmatter-parsing.md)) now that [Decide Core Engine / PowerShell Binding architecture split](https://github.com/HeyItsGilbert/mdbase-ps/issues/27) (recorded as [ADR-0002](../adr/0002-csharp-core-engine-powershell-binding.md)) moves the domain model into a portable C# library, `Mdbase.Core`, with **zero PowerShell dependency** — Yayaml, #5's recommendation, is itself a PowerShell module and is no longer an eligible candidate by construction.

Target: `Mdbase.Core`, `net8.0` (forward-compatible with .NET 10 LTS per [#2's amendment](https://github.com/HeyItsGilbert/mdbase-ps/issues/2#issuecomment-5154177302), the same TFM already confirmed for JsonSchema.Net and Celly), usable by any .NET consumer, no PowerShell hosting assumptions.

Sources for every candidate below were read directly from each library's own repository (`git clone --depth 1`, current default-branch tip) and cross-checked against its NuGet registry listing — not blog posts or aggregator summaries.

## What mdbase requires (spec Ch. 03 — Records And Frontmatter / YAML Profile; Ch. 04 — Configuration)

Unchanged in substance from #5 — the spec doesn't care which runtime parses its YAML, only what the parser is capable of:

- Parse UTF-8 Markdown frontmatter — the YAML mapping between the opening/closing `---` delimiters (`docs/reference/mdbase-spec-v0.3-current.md:744-746`).
- **"SHOULD use a safe YAML parser and MUST NOT execute custom tags"** (`mdbase-spec-v0.3-current.md:748-749`) — rules out any default deserialization path that resolves an arbitrary `!<...>` tag to a CLR type and instantiates it.
- **Scalar normalization to the JSON data model** before JSON Schema validation: mapping→object, sequence→array, string/integer/float/boolean/null (`mdbase-spec-v0.3-current.md:751-752`).
- **NaN, Infinity, binary values, and parser-specific timestamp objects MUST be explicitly handled by the mdbase YAML profile before schema validation, or rejected with a clear diagnostic** (`mdbase-spec-v0.3-current.md:752-755`) — the library's scalar/tag resolution has to be controllable enough that mdbase-ps's own code, not the library's default "smart" schema, decides what `.nan`, `.inf`, and a bare `2024-01-01` become.
- `mdbase.yaml` (`mdbase-spec-v0.3-current.md:757-762`) is itself a full YAML document (not a frontmatter fragment), parsed under the same profile — the chosen engine has to work for a whole document, not just an embedded mapping.
- Serialization (write path) — preserve unrelated body text/line endings, omit missing values, quote empty strings, preserve structure, deterministic key ordering — lower priority for this survey, same triage #5 applied; noted below, not blocking.

## What's different from #5

#5 surveyed *PowerShell-facing* options and found every candidate wrapped the same underlying library (YamlDotNet) — so the deciding factor wasn't YAML capability, it was **dependency/isolation policy**: take Yayaml because it had already solved loading YamlDotNet inside an Assembly Load Context to avoid colliding with `powershell-yaml`'s own bundled copy in the same PowerShell session, a problem bundling raw YamlDotNet directly in the module would have had to re-solve from scratch.

That axis is gone. `Mdbase.Core` has zero PowerShell dependency (ADR-0002) and isn't loaded into a shared PowerShell session alongside other modules that might bundle a conflicting YamlDotNet version — it's consumed by whatever .NET host references it. Whatever ALC-loading strategy mdbase-ps ends up using to load `Mdbase.Core.dll` and its transitive dependencies ([#29](https://github.com/HeyItsGilbert/mdbase-ps/issues/29), open) applies uniformly to every dependency — JsonSchema.Net, Celly, and the YAML library alike. It's a generic "how do we load this whole assembly" question now, not a YAML-specific differentiator between candidates the way it drove #5's Yayaml-over-raw-YamlDotNet conclusion.

What's new and genuinely hard: #5 could lean on Yayaml's own PowerShell-version gate (5.1 or 7.4+) and inherit YamlDotNet's TFM support indirectly, through a wrapper that already worked. This survey has to confirm each *pure* .NET candidate — not a wrapper — actually multi-targets `net8.0` as a first-class, currently-shipping target framework, verified directly against each library's own `.csproj`, not assumed by proximity to a PowerShell module that happened to work on the target runtime.

## Candidates surveyed

### YamlDotNet (`aaubry/YamlDotNet`) — recommended

- NuGet: `YamlDotNet` **18.1.0**, **MIT**, published 2026-06-26 (confirmed on nuget.org; the in-repo tag `v18.1.0` sits at commit `748334a`, 2026-06-22 — normal few-day tag-to-publish lag). `LICENSE.txt` carries the MIT grant for the library itself; a second file, `LICENSE-libyaml`, MIT-licenses ported libyaml scanner/parser logic (Kirill Simonov) — both permissive, no conflict with mdbase-ps's own MIT license.
- TFMs: `net10.0;net8.0;netstandard2.0;netstandard2.1;net47` (`YamlDotNet/YamlDotNet.csproj:4`) — `net8.0` **and** `net10.0` both explicit, first-class targets.
- Dependencies: **zero** at runtime. The only `PackageReference` is `Nullable` with `PrivateAssets="all"` (`YamlDotNet/YamlDotNet.csproj:40`) — a compile-time-only nullable-annotation shim for older TFMs that never flows to consumers. NuGet's own dependency listing shows nothing for any TFM.
- **Safe by default, with real history behind that default.** `YamlDotNet` ≤4.3.2 had exactly the classic YAML-deserialization RCE: `Deserializer.Deserialize()` would run `Type.GetType(nodeEvent.Tag.Substring(1), throwOnError: false)` on document-controlled tag content and blindly instantiate the result — [**CVE-2018-1000210**](https://nvd.nist.gov/vuln/detail/CVE-2018-1000210) / [GHSA-rpch-cqj9-h65r](https://github.com/advisories/GHSA-rpch-cqj9-h65r) (CVSS 7.8, high), fixed in 5.0.0. That exact mechanism still exists in 18.1.0, as `TypeNameInTagNodeTypeResolver` (`Serialization/NodeTypeResolvers/TypeNameInTagNodeTypeResolver.cs:35`, still doing `Type.GetType(nodeEvent.Tag.Value.Substring(1), throwOnError: false)`) — but the class is `[Obsolete]` (`:26`) and is **not** part of any default resolver chain; it only runs if a caller explicitly does `.WithNodeTypeResolver(new TypeNameInTagNodeTypeResolver())`.
- In its place, the default `DeserializerBuilder`'s `nodeTypeResolverFactories` list (`Serialization/DeserializerBuilder.cs:122-129`) unconditionally includes `PreventUnknownTagsNodeTypeResolver` (`Serialization/NodeTypeResolvers/RejectUnknownTagsNodeTypeResolver.cs:27`), which throws `YamlException` (`:33`) on any node carrying an explicit tag the earlier resolvers in the chain haven't already mapped — i.e. **an unrecognized/custom explicit tag is a hard parse-time error by default**, satisfying "MUST NOT execute custom tags" with zero mdbase-ps configuration. The only other default-registered `Type.GetType` call, `SystemTypeConverter` (`Serialization/Converters/SystemTypeConverter.cs:36`), is gated by `Accepts(Type type) => typeof(Type).IsAssignableFrom(type)` — it only fires when the *statically declared target type* is `System.Type` itself, never for `object`/dynamic map parsing, so it's unreachable from mdbase-ps's frontmatter-to-JSON-model path.
- **Scalar resolution control — no single "schema mode" switch, but complete, composable control at three layers:**
  1. **Low-level event stream** (`IParser`/`Scalar` events, `Core/Events/Scalar.cs:27-65`): every scalar exposes `Value` (raw string), `Tag` (raw, empty unless the document itself wrote one), `Style`, `IsPlainImplicit`/`IsQuotedImplicit` — zero implicit CLR typing at this layer. mdbase-ps could drive this directly for full manual control.
  2. **`RepresentationModel`** (`YamlStream`/`YamlMappingNode`/`YamlScalarNode`): the same guarantee, confirmed by reading `RepresentationModel/YamlScalarNode.cs:96-110` — `Value` is always `string?`; the tag is inspected separately; the only special-casing is a `forceImplicitPlain` bookkeeping flag for round-tripping implicit nulls (`~`, `null`) on re-emission, which never changes `.Value` itself.
  3. **High-level `Deserializer`** targeting `object`/`Dictionary<*,object>` (mdbase's actual shape): `ScalarNodeDeserializer` (`Serialization/NodeDeserializers/ScalarNodeDeserializer.cs:34`) is constructed with `attemptUnknownTypeDeserialization`, a field that **defaults to `false`** (`DeserializerBuilder.cs:63`, no initializer; only flipped by the opt-in `.WithAttemptingUnquotedStringTypeDeserialization()`, `DeserializerBuilder.cs:160-164`) — so **out of the box, every plain scalar parsed into `object` stays a raw string** (`ScalarNodeDeserializer.cs:133-135`, the `object`-typed branch defaults to `value = scalar.Value` unless the flag is set). That's a *stronger* guarantee than mdbase requires, not a weaker one: mdbase-ps gets a guaranteed-string baseline for free and layers its own JSON-Schema-aware bool/int/float/null normalization on top, instead of undoing a "smart" resolver's decision after the fact.
- If mdbase-ps *does* opt into `.WithAttemptingUnquotedStringTypeDeserialization()` for convenience, `AttemptUnknownTypeDeserialization` resolves null/bool/hex/octal/decimal-int/float explicitly, and separately resolves `.inf`/`-.inf`/`.nan` to `float.PositiveInfinity`/`NegativeInfinity`/`NaN` via two dedicated regex branches (`InfinityRegex`/`NotANumberRegex`, `ScalarNodeDeserializer.cs:41-42`) — easy to intercept before or instead of calling into this path. It **never** auto-resolves a bare timestamp-shaped string to `DateTime` in the dynamic path (no timestamp branch exists in `AttemptUnknownTypeDeserialization` at all; `DateTime` conversion only fires when the *target* type is statically `DateTime`, which dynamic map parsing never requests).
- Explicit-tag→CLR-type mapping is closed-world and opt-in: `TagNodeTypeResolver` only maps tags a caller registered via `WithTagMapping`, seeded by default with exactly six built-ins (`DeserializerBuilder.cs:79-86`: `!!map`→`Dictionary<object,object>`, `!!str`→`string`, `!!bool`→`bool`, `!!float`→`double`, `!!int`→`int`, `!!timestamp`→`DateTime`) drawn from the `FailsafeSchema`/`JsonSchema`/`DefaultSchema` tag-name constant classes (`Serialization/Schemas/FailsafeSchema.cs:26,36,49,56`). One correction to #5's characterization worth recording: those four "schema" classes are plain `static readonly TagName` constant containers, **not** a pluggable schema-mode object — there is no `.WithSchema(CoreSchema)`-style call anywhere in the API. #5 described YamlDotNet as exposing "schema classes ... that govern which tags a bare scalar resolves to" — directionally correct about the *outcome* (mdbase-ps can fully control scalar resolution) but attributing it to the wrong mechanism, most likely because #5 reasoned about YamlDotNet through Yayaml's wrapper rather than YamlDotNet's own source. The actual mechanism is the `NodeTypeResolver`/`NodeDeserializer` chain and the `attemptUnknownTypeDeserialization` flag documented above, verified here directly against source.
- Verdict: **recommended.**

### SharpYaml (`xoofx/SharpYaml`) — credible alternative, not recommended

- NuGet: `SharpYaml` **3.13.0**, **MIT**, published 2026-07-10 (`git describe --tags` on the cloned default-branch tip returns `3.13.0` directly — the repo's HEAD *is* the 3.13.0 release commit). `LICENSE.txt` carries SharpYaml's own MIT notice plus, since it started life as a 2013 fork of YamlDotNet, the original 2008-2012 Antoine Aubry MIT notice it forked from — both permissive.
- **Extremely active recently, but the whole API just changed.** The README states plainly: "SharpYaml v3 is a major redesign with breaking changes from v2. It uses a `System.Text.Json`-style API." Release cadence backs this up — 8 releases from 3.8.0 (2026-05-28) through 3.13.0 (2026-07-10), roughly weekly — but that means the entire `YamlSerializer`/`YamlSerializerOptions`/`YamlSerializerContext` surface examined below is about **three weeks old** as of this survey (2026-08-02).
- TFMs: `net10.0;net8.0;netstandard2.0` (`src/SharpYaml/SharpYaml.csproj:3`) — matches YamlDotNet's `net8.0`/`net10.0` coverage.
- Dependencies on `net8.0`: one real package, `System.Collections.Immutable [9.0.0, )` (confirmed both in `SharpYaml.csproj`'s unconditional `<PackageReference Include="System.Collections.Immutable" />` and in NuGet's own per-TFM dependency listing) — a Microsoft-owned package that ships in the shared framework since .NET 5, not a third-party transitive risk. `PolySharp` and `MinVer` are also referenced but both `PrivateAssets="all"` (analyzer/build-time only, never ship to consumers).
- **Schema/tag control is the one place SharpYaml ships exactly what #5 (imprecisely) attributed to YamlDotNet, and what mdbase's spec gestures at as the ideal shape**: a first-class `YamlSchemaKind` enum (`Failsafe`, `Json`, `Core`, `Extended` — `YamlSchemaKind.cs:10`) backed by real pluggable `SchemaBase`/`FailsafeSchema`/`JsonSchema`/`CoreSchema`/`ExtendedSchema` classes (`src/SharpYaml/Schemas/*.cs`), selected via `YamlSerializerOptions.Schema` (default `YamlSchemaKind.Core`, `YamlSerializerOptions.cs:184`) and gated by a separate `UseSchema` toggle (`YamlSerializerOptions.cs:193`, defaults `false`).
- **But the zero-config default is not spec-safe out of the box.** `YamlScalar.ResolveObject` (`Serialization/YamlScalar.cs:546`) is what backs the untyped/dynamic converter (`Serialization/Converters/YamlUntypedObjectConverter.cs:15`, `CanConvert(Type) => typeToConvert == typeof(object)` — mdbase's exact `Dictionary<string,object>`/`object` shape). When `UseSchema=false` (the default), `ResolveObject` still resolves plain scalars through `IsNull`→`TryParseBool`→`TryParseInt64`→`TryParseDouble`, unconditionally, no opt-in required. `TryParseDouble` (`YamlScalar.cs:304-325`, its own doc comment: *"Parses a YAML floating-point scalar into double, including .inf and .nan"*) explicitly matches `.inf`/`+.inf`/`-.inf`/`.nan` and returns `double.PositiveInfinity`/`NegativeInfinity`/`NaN` — **silently, with zero configuration** — exactly the "smart schema turns `.nan`/`.inf` into a native float" behavior mdbase's spec requires be intercepted first. (No bare-timestamp auto-resolution in this fast path, though — `ResolveObject`'s non-schema branch never checks for one, matching YamlDotNet's story on that specific axis.)
- Reaching YamlDotNet's zero-config safety baseline is possible, but takes two explicit settings: `UseSchema = true` **and** `Schema = YamlSchemaKind.Failsafe`. Verified via `FailsafeSchema`, which never overrides `PrepareScalarRules()` (so no rules are registered) and sets `AllowFailsafeString = true` — every plain scalar that matches no rule (there are none) falls back to the raw string, equivalent to YamlDotNet's default.
- Unrecognized/custom explicit tags are handled differently than YamlDotNet either way: traced through `TryResolveSchemaScalar`/`TryResolveExplicitTag` (`YamlScalar.cs:610-645`), both the default fast path and `UseSchema=true` mode **silently fall back to the plain/heuristic value rather than throwing** when a tag doesn't resolve in the active schema. Never executes or instantiates anything from the tag either way — safe, just quieter than YamlDotNet's throw-by-default, and less diagnosable for mdbase's "reject with a clear diagnostic" framing.
- SharpYaml carries the equivalent of YamlDotNet's historical CVE-2018-1000210 gadget, shipped more defensively labeled and, like YamlDotNet, off by default: `YamlSerializerOptions.UnsafeAllowDeserializeFromTagTypeName` (`YamlSerializerOptions.cs:206`, no initializer → defaults `false`; doc comment: *"should only be used with trusted YAML input"*) gates `YamlUntypedObjectConverter.TryReadUnsafeTaggedValue` (`Converters/YamlUntypedObjectConverter.cs:25,132,141`), which does exactly the `Type.GetType(tag.Substring(1))`-and-instantiate pattern the CVE describes. Opt-in only, and the property name itself is a loud, self-documenting warning label — arguably clearer API design than YamlDotNet's merely-`[Obsolete]` equivalent.
- One more behavioral note, not blocking: with the default `Schema=Core`, the untyped converter auto-enables YAML 1.1-style merge-key (`<<`) expansion (`YamlUntypedObjectConverter.cs:62-63,80`, `mergeEnabled = options.Schema is YamlSchemaKind.Core or YamlSchemaKind.Extended`) — a literal `<<` frontmatter key would be treated as a merge directive, not literal data, unless mdbase-ps also switches to `Failsafe`/`Json`.
- Verdict: **credible, faster, well-maintained alternative** — the closest literal match to an explicit schema-mode selector — but its zero-config default is exactly the footgun mdbase's spec warns against, reaching parity with YamlDotNet's default needs two settings mdbase-ps has to remember to set and keep set, and the entire v3 API is about three weeks old at time of writing. Not recommended as the primary pick today; worth a second look once v3 has run in production for a while (see follow-ups).

### VYaml (`hadashiA/VYaml`) — considered, not recommended

- NuGet: `VYaml` **1.4.0**, **MIT**, published 2026-06-21 (`Directory.Build.props:4` sets `PackageVersion` `1.4.0` directly; confirmed on nuget.org). The default branch has moved past the 1.4.0 tag since (`baa7c615`, 2026-07-06, "fix-incremental-generation") without a new release cut yet — actively maintained, just between releases.
- TFMs: `netstandard2.0;netstandard2.1;net6.0;net8.0;net9.0` (`VYaml/VYaml.csproj:3`) — `net8.0` present; no `net10.0` target yet, unlike YamlDotNet and SharpYaml. A `net8.0`-built assembly still runs unmodified on the .NET 10 runtime, the same forward-compatibility argument #2's amendment already accepted for JsonSchema.Net/Celly/YamlDotNet, so this alone isn't disqualifying.
- Dependencies on `net8.0`: one first-party dependency, `VYaml.Annotations [1.4.0, )` (confirmed on nuget.org; same-repo, same-version, attributes-only companion package — `[YamlObject]`/`[YamlIgnore]` etc.) — no third-party transitive dependency (the `System.Buffers`/`System.Memory`/`PolySharp` package references in `VYaml.csproj` are all `Condition="'$(TargetFramework)' == 'netstandard2.0'"`-gated, not present on `net8.0`).
- **Safe**: no reachable tag→arbitrary-type execution path for mdbase's use case. The one `Type.GetType()` call (`Serialization/Formatters/TypeFormatter.cs:29`) belongs to `TypeFormatter : IYamlFormatter<Type?>` (`:7`), selected only when the *statically declared* target type is `System.Type` — never reached deserializing into `object`/`Dictionary<object,object?>`. `Activator.CreateInstance` calls in `Serialization/Resolvers/BuiltinResolver.cs`/`GeneratedResolver.cs` build formatter instances from the **caller's own statically-declared C# type** (e.g. `type.GetElementType()`), never from YAML tag or document content.
- **Schema/tag control is where VYaml falls short of mdbase's needs — and its own source says so.** VYaml supports dynamic/untyped parsing (`YamlSerializer.Deserialize<object>`/`Deserialize<dynamic>`, README "Deserialize as dynamic" section) exclusively through `PrimitiveObjectFormatter` (`Serialization/Formatters/PrimitiveObjectFormatter.cs:10`), the only formatter registered for `typeof(object)`. Its scalar resolution is a **fixed, non-configurable** fallthrough: `IsNullScalar()` → `TryGetScalarAsBool` → `TryGetScalarAsInt32`/`Int64` → `TryGetScalarAsDouble` → string (`PrimitiveObjectFormatter.cs:135-158`) — with no schema/mode setting anywhere to change it. `TryGetScalarAsDouble` (`Internal/Scalar.cs:409`, byte-matched against `Inf0-2`/`NegInf0-2`/`Nan0-2` constants in `Internal/YamlCodes.cs:29-58`) resolves `.inf`/`.nan` to native `double` values **unconditionally, with no opt-out** — the same "silent smart-schema resolution" gap as SharpYaml's default, but here there is no `Failsafe`-equivalent switch to flip it off.
- More importantly, the switch statement in `PrimitiveObjectFormatter.Deserialize` is preceded by the library's own comment: `// TODO: checking tags` (`PrimitiveObjectFormatter.cs:133`) — a first-party admission that **the dynamic/object deserialization path does not currently consult a scalar's explicit YAML tag at all.** Quoted scalars are still safe — `Scalar.IsStringScalar()` (`Internal/Scalar.cs:594-596`) checks `Type is TokenType.DoubleQuotedScaler or SingleQuotedScaler` and every `TryGetBool`/`TryGetDouble`/etc. short-circuits on it first (`:196-198`, `:409-411`), so `"123"` correctly stays a string — but an explicit tag like `!!str 123` on a *plain* scalar is silently ignored rather than honored, and there is currently no way for mdbase-ps to intercept or reject an unrecognized custom tag in this path, because the path never looks at tags at all.
- No low-level node-tree/DOM API exists yet as an alternative escape hatch: the README's own roadmap lists "Support node tree representation" as an **unchecked** item. The raw `Utf8YamlTokenizer`/`YamlParser` types are public and do expose a per-scalar `Tag` (`Parser/YamlParser.TryGet.cs`, `TryGetCurrentTag`), so mdbase-ps *could* hand-write a fully custom `IYamlFormatter<object>` implementing Failsafe-equivalent control from these primitives — but that means building the control surface mdbase needs from scratch, where YamlDotNet and SharpYaml both already ship one.
- This isn't a surprise: VYaml's whole design center — source-generated `[YamlObject]` formatters, near-zero-allocation pooled UTF-8 scalars, README's own framing against Utf8Json/MessagePack-CSharp/MemoryPack — is optimized for the opposite of mdbase's problem. mdbase's frontmatter shape is unknown until a collection's type files are read at runtime; VYaml's fast path assumes the shape is a compile-time-known, attributed C# type.
- Verdict: **not recommended.** Safe (no execution risk) and genuinely fast, but its dynamic/untyped path — the one mdbase-ps would actually use for arbitrary frontmatter — is the least mature of the three, self-documented as incomplete on the exact axis (tag handling) this survey cares about most, with no schema controls and no ready low-level alternative.

## Recommendation

Take a direct dependency on **YamlDotNet 18.1.0** (MIT, zero runtime dependencies, `net8.0`/`net10.0` both first-class) for `Mdbase.Core`'s frontmatter and `mdbase.yaml` parsing — the same library #5 already traced mdbase's requirements against (through Yayaml's wrapper), now taken directly since `Mdbase.Core` has no PowerShell dependency to route through. Concretely: parse into `object`/`Dictionary<string,object?>` (or drop to the `RepresentationModel`/low-level `Parser` if per-node source-position information ends up mattering for the mdbase YAML profile's "reject with a clear diagnostic" requirement) using a `DeserializerBuilder` that leaves `attemptUnknownTypeDeserialization` at its default `false`. Every plain scalar then arrives as a string, and mdbase-ps's own JSON-Schema-driven normalization layer — mapping→object, sequence→array, and explicit bool/int/float/null coercion with NaN/Infinity/timestamp interception per Ch. 03 — owns 100% of the scalar-typing decision the spec requires, rather than adjudicating after the fact what a "smart" default already decided. The default resolver chain already throws on any unrecognized explicit tag (`PreventUnknownTagsNodeTypeResolver`), satisfying "MUST NOT execute custom tags" with no extra configuration, and the one mechanism capable of resolving a tag to an arbitrary CLR type (`TypeNameInTagNodeTypeResolver`) is `[Obsolete]`, not defaulted, and traces directly to the exact code path CVE-2018-1000210 patched out of the defaults in 2018 — mdbase-ps should simply never register it.

SharpYaml 3.13.0 is the strongest runner-up and worth remembering: it's faster on its own published benchmarks, its dependency footprint is nearly as small, and its `YamlSchemaKind.Failsafe/Json/Core/Extended` enum is the closest thing any candidate has to an explicit schema-mode selector. It loses to YamlDotNet here only because (a) its zero-config default silently resolves `.nan`/`.inf` to native doubles, which is precisely what the spec says must be intercepted first, and (b) its entire v3 API surface shipped about three weeks before this survey — real short-term stability risk for a dependency `Mdbase.Core` builds its whole frontmatter pipeline on. If SharpYaml's v3 API is still stable and its `Failsafe` schema is still the documented way to reach a string-only baseline a year from now, it's worth a second look purely on performance grounds. VYaml is not a fit today: its dynamic/object parsing path — the one part of mdbase-ps's actual workload it would exercise — is the one part of VYaml's own feature set that isn't finished (tag handling is a literal `// TODO` in its own source), with no schema control and no node-tree alternative to fall back on.

## Open follow-ups for later tickets (not blocking this survey)

- Whether mdbase-ps builds its NaN/Infinity/timestamp interception on top of YamlDotNet's raw `Parser`/`RepresentationModel` (maximum control, more code to write) or its high-level `Deserializer` with `attemptUnknownTypeDeserialization` left `false` (less code, same safety guarantee since every scalar already arrives as a string) is a frontmatter-parsing design-ticket decision, once the internal data model is settled — this survey confirms both paths give mdbase-ps everything the spec requires, not which is more ergonomic to build against.
- Whether/how `Mdbase.Core` vendors `YamlDotNet.dll` vs. takes a plain NuGet package reference is a distribution-ticket concern ([#29](https://github.com/HeyItsGilbert/mdbase-ps/issues/29), open) — the same question already deferred for JsonSchema.Net and Celly, now generalized per #29's own framing to "one entry assembly, normal .NET dependency resolution for the rest," not YAML-specific.
- Serialization/write-path requirements (preserve body/line endings, deterministic key ordering, quote empty strings) are Core Write/Lifecycle concerns, deferred exactly as #5 deferred them, until the v1 conformance-profile scope ticket determines whether write support ships in v1. Worth noting for that ticket: none of the three candidates has a first-class "preserve unrelated formatting on round-trip" feature — mdbase-ps's write pipeline will need to own body/line-ending preservation itself (straightforward, since frontmatter and body are serialized/reassembled separately) rather than expecting the YAML library to diff-and-patch a document in place.
- If SharpYaml's v3 rewrite (three weeks old at survey time) proves stable and its adoption grows, revisit this recommendation on performance grounds — nothing found here rules it out permanently, it just hasn't had time to prove itself yet as a foundational dependency.
- This survey did not evaluate write/round-trip fidelity in depth for any candidate (out of scope per the triage above); if Core Write ships in v1, re-examine YamlDotNet's `SerializerBuilder`/emitter configuration specifically for the Ch. 03 Serialization bullet list (omit-missing-values, quote-empty-strings, deterministic key ordering) before assuming it's free.
