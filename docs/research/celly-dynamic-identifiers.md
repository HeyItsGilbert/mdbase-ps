# Celly dynamic top-level identifier resolution for mdbase-ps

Research for [Research Celly's checker API for dynamic top-level identifier resolution](https://github.com/HeyItsGilbert/mdbase-ps/issues/17), part of the [mdbase-ps implementation plan](https://github.com/HeyItsGilbert/mdbase-ps/issues/1). Follows on from [#10 (Decide query engine design)](https://github.com/HeyItsGilbert/mdbase-ps/issues/10), which pinned the *contract* for bare top-level identifiers and deferred the *mechanism* here, and from [#4's survey](cel-implementations.md), which selected Celly as the CEL engine.

Sources read directly for this research: Celly's own internals/guide docs (`docs/internals/`, `docs/guide/`) and its C# source (`src/Celly/`), cloned from `bsidio/celly` at commit `c31c2774f4df7b9bbbf0786906b43b3015db8aa4` (2026-07-18) — the exact commit tagged `VersionPrefix 1.2.0`, i.e. the same `Celly 1.2.0` version already selected in [#4](cel-implementations.md). No claim below is sourced from the README alone; every mechanism claim cites a specific class/method/file.

## What mdbase requires (spec Ch. 10 — CEL Profile)

- **Bare top-level field access.** Ch. 10's Evaluation Contexts table grants "candidate raw fields at top level" (inferred match), "effective candidate fields at top level" (query/projection), and "current draft fields at top level" (lifecycle guard), each alongside the context's system bindings (`record`, `raw`, `present`, `file`, `note`, etc.). Worked examples confirm the bare form is the expected surface syntax, not just `record.<field>`:
  - Query context: `present.raw.status == false && record.status == "open"` (spec line 2661) — `status` used bare.
  - Match context: `file.inFolder("tasks") && present.raw.tags && tags.exists(t, t == "task")` (spec line 2692) — `tags` used bare, in the *same* expression as a `file.<method>()` receiver call.
- **Reserved-name collision rule.** "The system names `record`, `raw`, `present`, `file`, `note`, `projection`, `this`, `values`, `old`, `operation`, `event`, `workflow`, `trigger`, `steps`, `vars`, and `item` are reserved. A frontmatter field with one of those names remains available through `record.<field>` and `raw.<field>`." (spec lines 2654–2655) — a bare identifier that collides with a reserved name must resolve to the *system* binding, not the frontmatter field; #10 pinned this as "a reserved system name always wins the top-level slot on collision."
- **Field names are unknowable at `CelEnv` construction time.** They come from per-collection YAML frontmatter discovered at collection-load time, not from a fixed schema compiled into the module.
- **Fixed-shape `file`/link helpers, by contrast, are enumerable ahead of time.** Ch. 10's Link Host Functions: `link(value)`, `file.hasTag(tag)`, `file.hasLink(linkValue)`, `file.asLink()`, `linkValue.asFile()` (spec lines 2468–2472, repeated 2762–2770), plus the base-profile `file.inFolder(path)` (spec line 2762). "`file` supplies the candidate metadata and helpers defined by the collection, query, and link profiles" (spec line 2663) — the helper *set* is gated by which conformance profiles mdbase-ps ships, not discovered per collection the way frontmatter fields are. This is the "fixed shape... shouldn't need the same dynamic treatment" framing from #10/#17.
- **Everything still has to compile during preflight** (per [#4](cel-implementations.md)'s research): whatever mechanism resolves bare identifiers must still run through `CelEnv.Check`, not bypass it — a stored expression with a genuine type error must still be rejected before it's ever evaluated against a record.

## Mechanism A — free-identifier prescan via `AstTools.ReferencedVariables` (recommended)

Celly ships exactly this as a public, tested, documented API — not something to reconstruct.

- **`Celly.Ast.AstTools.ReferencedVariables(Expr expr) : IReadOnlySet<string>`** (`src/Celly/Ast/AstTools.cs:79`) walks a parsed `Expr` tree and returns "The free variable roots an expression references (comprehension-internal variables excluded)." For a dotted chain `a.b.c` it reports only the root `a` — exactly the granularity mdbase needs, since a bare frontmatter reference is a root identifier and any deeper path (`metadata.priority`) type-checks fine once the root is declared `dyn` (checker.md: "dyn stays dyn").
- **It operates on the parse output, before `Check` runs at all.** `env.Parse(text).Ast` is available the moment parsing succeeds; `AstTools.ReferencedVariables(ast.Expr)` needs nothing from the checker. Confirmed by both the guide (`docs/guide/ast.md:12-18`, `var ast = env.Parse(...).Ast!; AstTools.ReferencedVariables(ast.Expr);`) and by `AstToolsTests.ReferencedVariablesFindsFreeRoots` (`tests/Celly.Tests/Ast/AstToolsTests.cs:15-21`), which parses `"a.b + c && list.exists(x, x > threshold)"` via a bare `CelEnv.Default` (no declarations at all) and asserts the result is exactly `{a, c, list, threshold}`.
- **Comprehension variables are correctly excluded**, not just documented as excluded — `AstToolsTests.ComprehensionVariablesAreNotFree` is a dedicated test. Internally (`AstTools.cs:85-124`), `ReferencedVariables`'s `Walk` helper threads a scoped `bound` `HashSet<string>` through `ComprehensionExpr` nodes, adding `IterVar`/`IterVar2`/`AccuVar` before descending into the loop condition/step, and only `AccuVar` before descending into `Result` — i.e. it reimplements the checker's own comprehension-scoping rule (checker.md: "Comprehension variables shadow everything") purely at the AST level. `list.exists(x, x > threshold)` correctly yields `list` and `threshold`, not `x`.
- **It never picks up function names.** A call `size(x)` is a `CallExpr(target: null, function: "size", args: [x])` — the function name is a plain string field, not an `IdentExpr`, and `AstTools.Children` (`AstTools.cs:7-56`) only descends into `call.Target`/`call.Args`. So the prescan can't accidentally shadow a global function name.
- **Runtime wiring needs no special plumbing.** Once a name is declared (by any means — `VariableDecl` or otherwise), the planner (`src/Celly/Interpreter/Planner.cs:46-56`) compiles an `IdentExpr` into an `IdentEval` carrying its container-resolved candidate names; `IdentEval.Eval` (`src/Celly/Interpreter/Interpretables.cs:20-36`) does `activation.TryFind(name, ...)` per candidate — the exact same runtime path `record`/`raw`/`file` already use. This means the `MdbActivation` design from [#10](https://github.com/HeyItsGilbert/mdbase-ps/issues/10) (point 2: lazy `name -> Func<CelValue>` thunk dictionary) needs no bare-identifier-specific branch at eval time — `TryFind("status", ...)` and `TryFind("record", ...)` are the same kind of call; only the checker side needs the prescan.

**How to wire it in** (mirrors `docs/examples.md:335-363`'s "Handling untrusted expressions safely" recipe, which uses the same `ReferencedVariables` call for the *inverse* purpose — rejecting unknown names instead of declaring them):

1. `env.Parse(text)` → bail on parse errors as today.
2. `var free = AstTools.ReferencedVariables(parsed.Ast.Expr);`
3. Subtract every name already meaningful in that context: the context's reserved system names (`record`, `raw`, `present`, `file`, `note`, ... per the Ch. 10 table) *and* Celly's own standard type identifiers (see caveat below).
4. Build a `CelEnvSettings` that concatenates the context's base `Declarations` with `new VariableDecl(name, CelType.Dyn)` for each surviving free name.
5. `CelEnv.Create(settings).Check(parsed.Ast)` → reject on type errors as today; `.Program(ast)` to get the reusable `CelProgram`.

This is a **per-expression `CelEnv`**, not a single shared one — see the caveat below — but that's exactly mdbase's own "compile once at preflight" shape ([#4](cel-implementations.md), [#10](https://github.com/HeyItsGilbert/mdbase-ps/issues/10) point 5), so it isn't extra architecture, just where the per-expression `Declarations` list gets built.

### Caveats (implementation-ticket detail, not blocking this recommendation)

- **`CelEnv.Check` re-derives its `TypeEnv` from `Settings.Declarations` on every call** (`src/Celly/CelEnv.cs:93-123`) — it is not precomputed once at `CelEnv.Create` and cached. But `Settings` itself is fixed per `CelEnv` instance (assigned once in the private constructor, `CelEnv.cs:58`) and `Declarations` is `init`-only, so varying declarations *per expression* still means one `CelEnv` per distinct declaration set, built via `CelEnv.Create(settings)`. `CelEnvSettings` is a **plain `sealed class`, not a `record`** (`CelEnv.cs:11`), so there is no `with { Declarations = ... }` shortcut — the augmented settings object has to be built by copying `Container`/`Adapter`/`TypeProvider`/`ConfigureFunctions`/`FunctionDeclarations`/`Libraries`/`EvalLimits` explicitly alongside the concatenated `Declarations` list.
- **Must exclude Celly's own standard type identifiers from the Dyn-declare set**, not just mdbase's reserved names. `Checking.StandardDecls.CreateIdents()` (`src/Celly/Checking/StandardDecls.cs:220-234`) pre-declares `bool`, `int`, `uint`, `double`, `string`, `bytes`, `list`, `map`, `null_type`, `type`, `google.protobuf.Timestamp`, `google.protobuf.Duration` as root variables *before* `Settings.Declarations` is applied (`CelEnv.cs:104-112`). `Checking.TypeEnv.AddVariable` is a flat dictionary assignment (`Decls.cs:52`, `_variables[decl.Name] = decl` — last write wins). A frontmatter field literally named `int` or `list` would show up in `ReferencedVariables` and, if blindly declared `Dyn`, would silently clobber the real type identifier's `type(int)` type for that expression. The prescan filter must subtract this fixed list too (it's small and static, so a one-time constant in the implementation is enough — no need to query it dynamically).
- **No simpler built-in shortcut exists.** `Check` is optional in general (`docs/internals/architecture.md:31`: "the checker is optional... evaluation must work on unchecked ASTs") and `env.Parse` already returns an unchecked AST on its own — but mdbase's own preflight-compile requirement rules out just skipping `Check` (an unchecked AST would defer real type errors like `record.age + "x"` to a per-record runtime `ErrorValue` instead of rejecting the stored expression up front). There is no "permissive checker" flag anywhere on `CelEnvSettings`, and `Check` takes only the AST, not a per-call declarations override — confirmed by reading the entire public surface of `CelEnv` (`Parse`/`Check`/`EstimateCost`/`Program`/`Compile`, `CelEnv.cs:52-153`; matches `docs/guide/api.md`'s documented API 1:1). The prescan-then-declare pattern *is* the intended tool, not a workaround for a missing one.

## Mechanism B — AST rewrite of bare `Ident` into `Select` (possible, not recommended)

- **The building blocks are public and documented, not internals.** `Expr` node types are `public sealed class`es with ordinary public constructors — `IdentExpr(long id, string name)`, `SelectExpr(long id, Expr operand, string field, bool testOnly = false)` (`src/Celly/Ast/Expr.cs:27-40`). `docs/guide/ast.md:79-83` explicitly documents building ASTs programmatically this way ("ids just need to be unique within one expression"). Both types also appear in the snapshot-tested public API surface (`tests/Celly.Tests/ApiBaselines/PublicApi.Celly.txt:88-90,112-115`), so this isn't an accidental leak of internal types — Celly's own 1.0 "stable public API (snapshot-tested)" claim covers them.
- **But there is no built-in rewrite/transform utility to rewrite an *existing* parsed tree.** `AstTools` is read-only: `Children`, `DescendantsAndSelf`, `ReferencedVariables`, `CalledFunctions` (`AstTools.cs`, full contents read) — nothing constructs a modified copy of a tree. A grep across all of `src/Celly` for a visitor/rewrite/transform type or an exposed "next free id" helper on a parsed `CelAbstractSyntax` (`docs/internals`, `src/Celly` — searched for `Visitor`, `Rewrite`, `Transform`, `NextId`, `IdGenerator`) turns up nothing outside parse-time macro expansion.
- **Celly's own macros do this exact kind of rewrite internally — but only during parsing, with a facility that isn't exposed post-parse.** `BindingsLibrary.cs`, `OptionalsLibrary.cs`, `SmallLibraries.cs`, and the standard `has`/`map`/`filter` macro expanders in `Parsing/Macro.cs` all clone/rebuild subtrees exactly the way mechanism B describes (e.g. `Macro.cs:111-136`, `RewriteIndexRefs`, an 8-case recursive clone). They mint collision-free ids via `IMacroContext.NextId()` (`Parsing/Macro.cs:12`) — which is backed by the *parser's own* live id counter (`Parser.cs:219-222`, `private long NextId(int offset) { var id = ++_lastId; ... }`) because macro expansion runs *during* `env.Parse`, sharing that counter. A rewrite pass run *after* parsing completes (mechanism B, by construction — it needs the checker's reserved-name list, which is a runtime concern, not something a macro can see) has no access to that counter; it would need its own id-uniqueness scheme (e.g. tracking `AstTools.DescendantsAndSelf(ast.Expr).Max(n => n.Id)` and minting upward from there).
- **The transform itself would have to reimplement `ReferencedVariables`'s own comprehension-shadowing logic**, node kind by node kind (`ConstExpr` passthrough, `IdentExpr` → rewrite-or-passthrough, `SelectExpr` → recurse into `Operand`, `CallExpr` → recurse `Target`/`Args`, `ListExpr`/`MapExpr`/`StructExpr` → recurse elements/entries/fields, `ComprehensionExpr` → recurse 5 sub-expressions while *not* rewriting `IterVar`/`AccuVar`/`IterVar2` references) — otherwise `list.exists(x, x > threshold)` gets corrupted into `list.exists(x, record.x > record.threshold)`.
- **Injected nodes lose position info.** `SourceInfo.PositionOf` (`Ast/SourceInfo.cs:31`) falls back to `-1` for any expression id it has no entry for; a hand-built `SourceInfo` for a rewritten tree would either need to track positions for synthetic `record`-ident nodes (there is no source position for a node that didn't appear in the original text) or accept degraded error-location diagnostics for them specifically.
- **Verdict:** technically supported (nothing in the API blocks it, and it's not a misuse of internals), but it reaches the *same* end state as mechanism A — a bare name that resolves like `record.<name>` against a `Dyn`-typed map — through a hand-rolled, undocumented-as-a-recipe, multi-case tree transform with real edge cases (id collisions, comprehension-shadowing reimplementation, source-position gaps) that Celly gives away for free via `ReferencedVariables`. Not worth building.

## Mechanism C — checker-native dynamic/unbound-identifier hook (does not exist)

- **No such hook exists.** A search of `docs/internals/checker.md` and all of `src/Celly` for anything resembling a permissive mode, dynamic container, or unknown-identifier resolver (`Permissive`, `AllowUnknown`, `AllowUndeclared`, `IUnknownResolver`, `DynamicContainer`, `IContainerResolver`, "unbound identifier", "fallback") returns nothing.
- **`Checker.CheckIdent` is unconditional** (`src/Celly/Checking/Checker.cs:158-188`): it tries the comprehension scope, then declared variables via container-qualified candidate names (`scope.FindVariable`/`FindRootVariable`), then `ITypeProvider.FindIdent`, and if none hit: `Report(ident, $"undeclared reference to '{ident.Name}'" ...); return CelType.Error;`. There is no branch that treats "nothing matched" as anything other than a hard checker error — no override point, no injected resolver callback, no settings flag to change this behavior.
- **The one lookalike extension seam is a trap, not a mechanism.** `ITypeProvider.FindIdent(string name) : CelValue?` (`src/Celly/Providers/ITypeProvider.cs:20`) looks at first glance like it could resolve "any unknown name" dynamically, but its own doc comment scopes it precisely: "Provider identifiers: enum constants (int values) and message type names (type values)." Confirmed at the planner level: `Planner.StaticFallback` (`src/Celly/Interpreter/Planner.cs:159-176`) is doc-commented "**Plan-time constant** resolution: standard type idents, then provider idents" — a `FindIdent` hit is baked into the compiled program as a fixed `CelValue` *once, at plan time*, exactly like an enum constant (`Tier.Pro`) is. It never becomes an `IdentEval` that calls `activation.TryFind` per evaluation. A custom `ITypeProvider` that returned a placeholder `Dyn` value for any unknown name would make the checker accept the expression, but every record would then evaluate that identifier to the *same frozen value chosen once at compile time* — not `record["status"]` re-read per record. For mdbase's per-record dynamic field lookup this is actively wrong, not just unsupported.
- **Verdict:** mechanism C, as literally described in the ticket, does not exist in Celly 1.2.0.

## Secondary confirmation — `NativeTypeProvider` for fixed-shape `file`/`MdbLink` helpers

Confirmed, with one important precision the issue's README-derived framing glosses over: **`NativeTypeProvider` binds properties, not methods.**

- `NativeTypeProvider`'s registration path reflects with `type.GetProperties(BindingFlags.Public | BindingFlags.Instance)` (`src/Celly/Providers/NativeTypeProvider.cs:62-66`) and nothing else — there is no `GetMethods` call anywhere in its 743-line source. `docs/guide/native-types.md` documents exactly this surface: construction (`## Construction`), field-name aliasing (`## Field names`), a property-only `.NET → CEL` type-mapping table (`## Type mapping`), presence (`## Presence (has())`), and field-wise equality (`## Equality`) — no section on exposing instance methods, because there isn't one.
- **Instance methods are a completely separate mechanism: ordinary receiver-style function declarations**, the same mechanism Celly uses for its *own* standard library. `docs/guide/api.md`'s "Custom functions" section states it directly: "Receiver-style calls (`x.f(y)`) dispatch to the same name with the receiver as `args[0]`." The checker side is a `FunctionDecl`/`OverloadDecl(..., isInstance: true)` (`src/Celly/Checking/Decls.cs:14-24`) with the receiver's declared type as `argTypes[0]`; the runtime side is `FunctionRegistry.Register(name, Func<CelValue[], CelValue>)` (`src/Celly/Stdlib/FunctionRegistry.cs:12`, whose own comment on `size` reads "both global `size(x)` and receiver `x.size()` dispatch here (receiver is arg 0)"). Celly's extension libraries use this pattern extensively for receiver-style methods on non-map types — e.g. `StringsLibrary.cs:25` (`charAt`), `NetworkLibrary.cs:58-76` (`ip('...').isGlobalUnicast()`, `cidr('...').containsIP(...)`) — confirming it's the idiomatic way to give *any* CEL value receiver-style methods, whether the receiver is a struct, an opaque type, or (per this recommendation) a `NativeTypeProvider`-registered class.
- **The bridge back to the real C# instance is `CelValue.ToNative()`**, an `abstract` member every `CelValue` subtype implements (`src/Celly/Values/CelValue.cs:23`). `NativeTypeProvider`'s own struct wrapper, `NativeObjectValue`, implements it as `public override object ToNative() => _instance;` (`NativeTypeProvider.cs:681`), returning the exact wrapped .NET object. So a registered function implementation for `inFolder` can do `args[0].ToNative()`, cast it to the known C# type (`MdbFile`), and call the real `.InFolder(path)` method — the type-checker validates the call shape via the declared `OverloadDecl`, and the registered lambda does the actual dispatch.
- **Net answer:** `NativeTypeProvider` is the right tool to give `file` and `MdbLink` CEL **struct-type identity** — a `CelType.Struct(...)` to declare them as (`Declarations = [new VariableDecl("file", CelType.Struct("Mdbase.MdbFile"))]`, mirroring `docs/guide/native-types.md:30-36`'s own example), plus `has()`/equality/construction and typed access to any plain properties they carry (e.g. a `file.path`-style field, if one exists) — for free, via reflection, with checker-validated field types. It is **not** how `inFolder(path)`/`hasTag(tag)`/`hasLink(linkValue)`/`asLink()`/`asFile()` get exposed; those need hand-declared receiver-style `FunctionDecl`/`OverloadDecl`s (checker signatures) plus hand-registered `FunctionRegistry` implementations (runtime bodies unwrapping via `ToNative()`), exactly like every other receiver method in Celly's own standard library. Both pieces are needed together — `NativeTypeProvider` supplies the receiver *type* the overloads are declared against, not the methods themselves.

## Recommendation

**Build on mechanism A** — parse, prescan with `Celly.Ast.AstTools.ReferencedVariables`, filter out reserved context names and Celly's fixed standard-type-identifier list, declare the remainder `CelType.Dyn` on a per-expression `CelEnvSettings`, then `Check`/`Program` as already planned. It is the only one of the three mechanisms that is both genuinely well-supported (a documented, public, unit-tested, one-call API — the same call Celly's own docs recommend for the mirror-image "reject unknown identifiers" problem) and simple (no AST reconstruction, no new runtime plumbing — bare identifiers flow through the exact same `IdentEval`/`IActivation.TryFind` path reserved names already use, so [#10](https://github.com/HeyItsGilbert/mdbase-ps/issues/10)'s planned `MdbActivation` needs no bare-identifier-specific branch). Mechanism B reaches the same outcome only after reimplementing, by hand, logic Celly already ships (comprehension-shadowing, id-uniqueness, source positions) with no first-class support for rewriting a parsed tree. Mechanism C — a checker-side hook that resolves unknown identifiers dynamically against a supplied resolver — does not exist in Celly 1.2.0, and the closest-looking substitute (`ITypeProvider.FindIdent`) is a plan-time-constant mechanism that would silently freeze every bare field to one value across all records, not a per-record lookup.

The two caveats under mechanism A above (exclude standard type idents, not just mdbase's reserved names; build the augmented `CelEnvSettings` by copying fields since it's a plain class) are real but small, and belong in the implementation ticket, not this one.

For `file`/`MdbLink`: register them via `NativeTypeProvider` for struct identity/`has()`/equality/property access, and declare their helper methods (`inFolder`, `hasTag`, `hasLink`, `asLink`, `asFile`) as ordinary receiver-style `FunctionDecl`/`OverloadDecl(isInstance: true)` entries with `FunctionRegistry` implementations that unwrap the receiver via `CelValue.ToNative()` — the same two-mechanism combination Celly uses for its own stdlib, not a single NativeTypeProvider call.

## Open follow-ups for later tickets (not blocking this research)

- The exact reserved-name/standard-type-ident exclusion list to bake into the prescan filter (a per-context reserved set from Ch. 10's table, plus the fixed 12-name `StandardDecls.CreateIdents()` list) is implementation-ticket detail.
- Whether to build one `CelEnv` per stored expression unconditionally, or cache/dedupe `CelEnv`s across expressions that happen to prescan to the same free-identifier set, is a preflight-compile performance detail for the implementation ticket — both are correct, this is purely a cost question.
- The concrete `NativeTypeProvider` struct shape for `file`/`MdbLink` (which properties they carry, if any, beyond their method surface) and the exact `FunctionDecl`/`OverloadDecl` signatures for `inFolder`/`hasTag`/`hasLink`/`asLink`/`asFile` belong to the file/link-profile implementation ticket — this research only confirms the *mechanism*, not the shape.
- Null/absent semantics for a bare field that doesn't exist in a given record's frontmatter (what `MdbActivation.TryFind` returns — `NullValue`, an "unset" sentinel, etc.) is [#10](https://github.com/HeyItsGilbert/mdbase-ps/issues/10)'s `MdbActivation` design territory, not re-litigated here — this research only establishes that the *checker* will accept the bare reference.
